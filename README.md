# GAME

سامانهٔ فارسی رقابت استراتژیک دو تیم ایران و آمریکا. تمام قلمروها، شخصیت‌ها، سازه‌ها و حرکت‌ها ساختگی‌اند. هیچ دادهٔ جغرافیایی، نظامی یا خصوصی واقعی در سناریو وجود ندارد.

**وضعیت تحویل:** کد Frontend و Backend پیاده‌سازی و به‌صورت محلی آزمایش شده است. اتصال Supabase و تأیید انتشار عمومی، جداگانه به تنظیم محیط مقصد نیاز دارند. بدون پیکربندی معتبر، صفحهٔ ورود این موضوع را صریح نمایش می‌دهد؛ دادهٔ نمایشی جایگزین سرور نمی‌شود.

[گزارش تحویل و محدودیت‌های تأییدشده](docs/DELIVERY.fa.md) · [معماری و قراردادهای امنیتی](docs/ARCHITECTURE.fa.md) · [آزمون استقرار](docs/ACCEPTANCE.fa.md)

## اجرای Frontend

Node.js نسخهٔ ۲۴ و npm لازم است.

```bash
npm ci
cp .env.example .env.local
npm run dev
```

در `.env.local` فقط نشانی پروژه و **کلید عمومی publishable یا anon** را وارد کنید. مسیر توسعه با پایهٔ پیش‌فرض: `http://localhost:5173/game/`.

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_ANON_KEY=your-public-publishable-key
VITE_BASE_PATH=/game/
```

کلید `service_role`، کلید `sb_secret_`، رمز حساب‌ها و توکن مدیریت Supabase نباید در متغیرهای `VITE_`، مخزن یا خروجی build قرار بگیرند. تابع ساخت کلاینت، کلیدهای سرور را رد می‌کند. فونت Vazirmatn داخل build بسته‌بندی می‌شود و به CDN خارجی وابسته نیست.

## راه‌اندازی Supabase

یک پروژهٔ **اختصاصی بازی و بدون جدول‌های هم‌نام** انتخاب کنید. migrations این مخزن برای نصب تازه طراحی شده‌اند. قبل از اجرا روی دیتابیس موجود، schema و سیاست‌ها را بررسی کنید.

```bash
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase db push --dry-run
npx supabase db push
```

تنظیمات `supabase/config.toml` را برای محیط مقصد بازبینی کنید؛ این فایل ثبت‌نام عمومی را می‌بندد، طول رمز را ۱۲ تعیین می‌کند و URL بازگشت را برای مخزن فعلی تنظیم کرده است. برای پروژهٔ اختصاصی می‌توان پس از بررسی از دستور زیر استفاده کرد:

```bash
npx supabase config push
```

در داشبورد Authentication نیز غیرفعال‌بودن signup، تنظیم SMTP برای بازیابی، حداقل طول و قواعد رمز، Site URL و Redirect URLs را کنترل کنید. Site URL تولید: `https://gptyar-web.github.io/game/`. برای دامنهٔ اختصاصی آن را تغییر دهید.

چهار Edge Function را منتشر کنید:

```bash
npx supabase functions deploy auth-session
npx supabase functions deploy game-command
npx supabase functions deploy admin-users
npx supabase functions deploy engine-tick
```

`verify_jwt=false` برای این ورودی‌ها در config ثبت شده است. `game-command` و `admin-users` خودشان با `auth.getUser(token)` اعتبار JWT را بررسی می‌کنند؛ `auth-session` ورودی عمومی احراز هویت با محدودیت تلاش است. `engine-tick` فقط با راز اختصاصی زمان‌بند کار می‌کند و برای پردازش اصلی Cron لازم نیست.

Secrets محیط Edge:

| متغیر                | مقدار / کاربرد                                                  |
| -------------------- | --------------------------------------------------------------- |
| `ALLOWED_ORIGINS`    | فهرست originها با ویرگول؛ تولید: `https://gptyar-web.github.io` |
| `APP_URL`            | `https://gptyar-web.github.io/game/`؛ بازگشت بازیابی حساب       |
| `ENGINE_TICK_SECRET` | اختیاری؛ راز تصادفی حداقل ۳۲ نویسه برای زمان‌بند خارجی          |

متغیرهای استاندارد `SUPABASE_URL`، `SUPABASE_ANON_KEY` و `SUPABASE_SERVICE_ROLE_KEY` در محیط امن Edge استفاده می‌شوند؛ هیچ‌کدام از کلیدهای خصوصی را به Frontend منتقل نکنید.

migrations، جدول‌های بازی را با RLS و دسترسی فقط‌خواندنی مستقیم می‌سازند. Realtime فقط برای `game_events` و `matches` فعال می‌شود. جدول‌های خام جنگنده، هدف و منابع به publication اضافه نمی‌شوند.

## پردازش بدون مرورگر

در صورت موجودبودن `pg_cron`، migration یک job با نام `game-engine-tick` و فاصلهٔ ۱۰ ثانیه می‌سازد. کار زمان‌بند شامل شروع مسابقات زمان‌دار، پایان مأموریت، بازگشت واحد، اتمام تعمیر و پایان مسابقه است.

پس از نصب، در SQL Editor بررسی کنید:

```sql
select jobid, jobname, schedule, active
from cron.job
where jobname = 'game-engine-tick';

select jobid, status, start_time, end_time
from cron.job_run_details
order by start_time desc limit 10;
```

اگر extension موجود نباشد، job ساخته نمی‌شود و باید پیش از استفادهٔ آنلاین Cron را فعال کنید یا `engine-tick` را با زمان‌بند خارجی و راز اختصاصی فراخوانی کنید. RPC `game_snapshot` نیز بازیابی و پردازش عقب‌مانده را انجام می‌دهد، اما جایگزین آزمون زمان‌بند مستقل نیست.

## ایجاد امن حساب‌های اولیه

هیچ حساب یا رمز ثابتی در seed یا کد وجود ندارد.

۱. پس از اجرای migrations، اسکریپت `scripts/bootstrap.mjs` را از یک محیط مدیریتی امن اجرا کنید. یک شیء JSON با فیلدهای `url`، `service_key`، `username` و ایمیل اختیاری `email` از **stdin** دریافت می‌کند. ورودی را از secret manager بفرستید؛ آن را در فایل مخزن، آرگومان shell یا تاریخچهٔ فرمان ذخیره نکنید.

۲. اسکریپت، اولین مدیر را با Supabase Auth می‌سازد. رمز تصادفی فقط یک‌بار در خروجی همان اجرای امن تحویل می‌شود. آن را در password manager نگه دارید. اگر مدیر قبلاً وجود داشته باشد، اسکریپت از ساخت مدیر دیگر جلوگیری می‌کند.

۳. مدیر وارد سامانه می‌شود و رمز اولیه را تغییر می‌دهد. تغییر نقش یا داده‌های تیمی پیش از تغییر واقعی hash رمز در Supabase Auth مجاز نیست.

۴. در پنل «مدیریت ← کاربران»، دو حساب بازیکن برای ایران و آمریکا بسازید. رمزها در Edge ساخته می‌شوند و فقط در پنجرهٔ یک‌بارمصرف نمایش داده می‌شوند. ایمیل بازیابی اختیاری است؛ بدون آن بازیابی ایمیلی ممکن نیست.

۵. مسابقه بسازید و کاربران را به تیم و نقش `commander` یا `operator` اختصاص دهید. مدیر برای بازی‌کردن نیز باید عضو یک تیم باشد. حساب `spectator` حتی با عضویت عملیاتی قدیمی، اطلاعات محدود و دسترسی فقط‌خواندنی دارد.

## سناریوی اولیه

ایجاد مسابقه از پنل مدیر، یک سناریوی مستقل می‌سازد: دو تیم، ۱۴ سازهٔ خیالی، ۶ جنگنده شامل یک رادارگریز آمریکا، دو واحد دفاعی، دو شخصیت داستانی و منابع اولیه. سازه‌های سالم و آسیب‌دیده وجود دارند. شروع دستی مسابقهٔ آزمایشی، یک تعمیر واقعی با کسر منابع ثبت می‌کند.

بازنشانی فقط برای همان مسابقهٔ `is_test=true` در وضعیت غیر در حال اجرا مجاز است. مسابقات دیگر و حساب‌ها دست‌نخورده می‌مانند. ایجاد مسابقهٔ مشابه، قوانین قبلی را به یک سناریوی جدید کپی می‌کند.

## GitHub Pages

در مخزن `gptyar-web/game`:

۱. از `Settings → Pages`، منبع انتشار را **GitHub Actions** انتخاب کنید.
۲. در `Settings → Secrets and variables → Actions → Variables`، مقادیر عمومی `VITE_SUPABASE_URL` و `VITE_SUPABASE_ANON_KEY` را ثبت کنید. `VITE_BASE_PATH` اختیاری است و پیش‌فرض `/game/` دارد؛ دامنهٔ اختصاصی معمولاً `/` می‌خواهد.
۳. workflow «Verify and deploy GAME» را اجرا کنید یا روی `main` push کنید.

workflow آزمون‌های UI و PostgreSQL، build، بررسی نبودن کلید سرور در bundle و بررسی TypeScript چهار Edge Function را اجرا می‌کند. سپس artifact را با مجوزهای `pages:write` و `id-token:write` منتشر می‌کند. مسیریابی `HashRouter` با مسیر `/game/#/...` سازگار است.

بدون متغیرهای Supabase، build موفق است ولی ورود صریحاً غیرفعال می‌ماند؛ این حالت به معنی اتصال یا تکمیل بازی آنلاین نیست. فایل workflow به‌تنهایی Pages را در تنظیمات مخزن فعال نمی‌کند.

## آزمون‌ها

```bash
npm run check
npm run test:edge
node scripts/check-public-build.mjs
```

- ۹ آزمون Vitest برای رابط ورود، مرز کلید عمومی، نمایش خطا و محاسبهٔ زمان.
- ۳۸ آزمون integration/security با PostgreSQL واقعی در PGlite؛ schema و توابع همان migrations تولید هستند. `auth.uid()` و جدول حداقلی Auth در آزمون شبیه‌سازی می‌شوند؛ این آزمون، سرویس واقعی Auth یا شبکهٔ Realtime را تأیید نمی‌کند.
- بررسی Deno برای چهار Edge Function؛ این بررسی جای اجرای آن‌ها در Supabase را نمی‌گیرد.

`npm run test:live` یک سناریوی آزمایشی مستقل می‌سازد و ورود، RLS، ثبت هم‌زمان یک درخواست، رادارگریز، دفاع دستی، Realtime و تکمیل کارها در زمان قطع ارتباط را روی **Supabase واقعی** می‌آزماید. ورودی محرمانهٔ آن از stdin دریافت می‌شود؛ فیلدها در ابتدای اسکریپت مستندند. سه حساب فعال با رمز تغییریافته لازم‌اند. این آزمون تا پیکربندی محیط مقصد اجراشده محسوب نمی‌شود.

## پشتیبان و نگهداری

«پشتیبان منطقی مسابقه» تمام ردیف‌های بازی همین مسابقه را از RPC مخصوص مدیر صادر می‌کند، بدون رمزها، ایمیل‌های Auth یا کلیدها. این خروجی برای دادهٔ بازی است و جای پشتیبان کامل Supabase و Auth را نمی‌گیرد. بازیابی خودکار JSON دلخواه در نسخهٔ فعلی ارائه نشده است؛ بازیابی سناریوی آزمایشی با reset و ساخت مجدد سناریوی مستقل انجام می‌شود.

رویدادها، تراکنش‌ها و Audit Log ثبت می‌شوند. خطای پردازش زمان‌بند برای یک مسابقه، با SQLSTATE غیرحساس ثبت می‌شود و پردازش مسابقات دیگر ادامه می‌یابد. خطاهای زیرساخت Edge و ارسال ایمیل را از Logs داشبورد Supabase بررسی کنید.
