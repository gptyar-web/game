# معماری GAME

## مرزهای اجرا

| لایه       | فناوری                                                          | مسئولیت                                                        |
| ---------- | --------------------------------------------------------------- | -------------------------------------------------------------- |
| رابط       | React، TypeScript، Vite، Tailwind، Radix/shadcn، Lucide، Motion | نمایش RTL، رادار و فرم‌های اقدامات                             |
| دادهٔ سرور | TanStack Query                                                  | cache به تفکیک کاربر، مسابقه و نمای مدیر؛ بازیابی پس از اتصال  |
| وضعیت شخصی | Zustand                                                         | صدا، افکت‌ها، راهنما و نشانگر انتخاب‌شده؛ بدون تصمیم بازی      |
| هویت       | Supabase Auth و `auth-session`                                  | تطبیق نام کاربری با حساب Auth، ورود و بازیابی بدون افشای ایمیل |
| مجوز       | PostgreSQL RLS و توابع schema خصوصی                             | نقش از `profiles` و `match_members`؛ هرگز از `user_metadata`   |
| فرمان      | `game-command` → RPC invoker → تابع خصوصی معتبرسنجی‌شده         | اعتبار JWT، مجوز، وضعیت مسابقه، تراکنش و idempotency           |
| پردازش     | PostgreSQL و Cron                                               | نتیجهٔ انتزاعی، آسیب، دفاع، تعمیر، زمان‌بندی و نتیجهٔ نهایی    |
| رویداد     | Realtime روی `game_events` و `matches`                          | ارسال رویدادهای دارای مخاطب و invalidation داده‌های مجاز       |
| میزبانی    | GitHub Pages                                                    | فقط Frontend؛ بدون کلید سرور یا موتور معتبر در مرورگر          |

## مدل داده

۲۵ جدول در schema عمومی ساخته می‌شوند و همگی RLS دارند:

| گروه                | جدول‌ها                                                                               |
| ------------------- | ------------------------------------------------------------------------------------- |
| هویت و عضویت        | `profiles`, `teams`, `match_members`                                                  |
| مسابقه و تنظیمات    | `matches`, `game_settings`, `system_settings`, `structure_types`                      |
| دارایی و داستان     | `structures`, `fictional_characters`, `aircraft`, `defense_units`                     |
| اطلاعات مجاز        | `intel_contacts`, `mission_signals`                                                   |
| عملیات              | `missions`, `mission_events`, `defense_events`, `repair_jobs`                         |
| اقتصاد و امتیاز     | `team_resources`, `resource_transactions`, `match_scores`                             |
| رویداد و ثبت فعالیت | `game_events`, `notifications`, `notification_reads`, `audit_logs`, `action_requests` |

`game_private.auth_attempts` جدول داخلی محدودیت ورود است. UUID برای شناسه‌های اصلی استفاده می‌شود؛ `game_events.seq` شمارندهٔ مرتب‌سازی رویداد است. روابط مربوط به دارایی‌ها دارای FK مرکب با `match_id` هستند تا از اتصال دارایی دو مسابقه جلوگیری شود. سلامت، نوع رادارگریز، منابع غیرمنفی و یکتایی عملیات فعال constraint دارند.

## تراکنش و تکرار درخواست

هر فرمان ابتدا هویت و عضویت فعلی را بررسی می‌کند، ردیف مسابقه را با `FOR UPDATE` قفل می‌کند و کلید idempotency را قفل می‌کند. درخواست با همان کاربر، شناسه، action و payload همان پاسخ را می‌گیرد. استفاده از شناسهٔ قبلی با دادهٔ متفاوت رد می‌شود.

رزرو جنگنده، کسر منابع، مأموریت، اعلان، رویداد، دفتر منابع و Audit Log در یک تراکنش انجام می‌شوند. خطای هر مرحله همهٔ تغییرات فرمان را برمی‌گرداند. مرورگر شناسهٔ درخواست ناموفق در شبکه را در sessionStorage همان کاربر حفظ می‌کند تا retry پس از reload نیز همان intent را بفرستد. درخواست موفق از این حافظه حذف می‌شود.

یک جنگنده فقط یک مأموریت فعال و هر دارایی فقط یک تعمیر فعال دارد. قفل مسابقه، هزینهٔ سازگاری را برای مقیاس کوچک تیمی ساده می‌کند؛ پیش از استفادهٔ پرترافیک، آزمون بار و بررسی contention لازم است و انجام‌شده گزارش نمی‌شود.

## مجوز و اطلاعات مخفی

کلاینت فقط SELECT دارد و هیچ مجوز مستقیم INSERT/UPDATE/DELETE روی داده‌های بازی ندارد. RLS دارایی‌ها را به تیم مالک محدود می‌کند. جزئیات تیم مقابل از `intel_contacts` دریافت می‌شود؛ hidden هیچ ردیفی نمی‌سازد و unknown مختصات، نوع و سلامت ندارد.

ماموریت و هواپیمای رادارگریز آمریکا در جدول خام فقط برای مالک و مدیر قابل‌خواندن‌اند. تیم مقابل یک `mission_signal` پالایش‌شده بدون مبدأ، مقصد یا مختصات می‌گیرد. هیچ‌یک از مختصات به‌صورت مخفی در DOM یا state مرورگر تیم مقابل قرار نمی‌گیرند. پایان اختلال موقعیت مخفی را افشا نمی‌کند.

توابع عمومی `SECURITY INVOKER` هستند. توابع نیازمند اختیار در `game_private` با `search_path=''` قرار دارند. EXECUTE پیش‌فرض از PUBLIC و anon پس گرفته شده است. فقط helperهای RLS و ورودی‌های معتبرسنجی‌شده برای authenticated مجازند. worker فقط به service_role اعطا شده است. هر ورودی خصوصی قابل فراخوانی توسط کاربر، `auth.uid()` و مجوزهای فعلی را بررسی می‌کند.

تعلیق حساب و تغییر تیم/نقش در هر درخواست از دیتابیس بررسی می‌شوند؛ باقی‌ماندن JWT قبلی به کاربر امکان دورزدن نقش جدید نمی‌دهد. Spectator عمومی حتی با عضویت قدیمی اپراتور، تیم مؤثر و مجوز عملیات دریافت نمی‌کند.

## زمان و منطق بازی

مأموریت و تعمیر دارای شروع و پایان سرور هستند. حرکت روی شبکه صرفاً interpolation خطی برای نمایش است. احتمال دفاع از تنظیمات مصنوعی، سطح و امتیاز دفاعی بازی می‌آید. هیچ محاسبهٔ برد، رهگیری، بالستیک، هدایت یا جغرافیای واقعی وجود ندارد.

انتخاب ناحیه در دفاع دستی یک انتخاب بازی است و به موقعیت واقعی یا حتی مختصات مخفی جنگنده وابسته نیست. یک فرصت مصرف می‌شود و درخواست دوم رد می‌شود. در مدت اختلال بازی، دفاع خودکار کنار گذاشته می‌شود. بعد از انقضا، هشدار پاک می‌شود.

Cron هر ۱۰ ثانیه کارهای سررسیدشده را پردازش می‌کند. خواندن snapshot نیز عقب‌ماندگی را جبران می‌کند. توقف مسابقه پردازش زمانی را متوقف می‌کند؛ ادامهٔ مسابقه زمان‌های پایان را به اندازهٔ توقف منتقل می‌کند. پایان مسابقه نتیجه را تثبیت و عملیات ناتمام را می‌بندد.

## تاریخچه، نمودار و پشتیبان

رویدادهای تیمی snapshot مجاز همان تیم را شامل می‌شوند. Replay زمان و سرعت نمایش را تغییر می‌دهد و هیچ فرمانی برای تغییر بازی صادر نمی‌کند. مرور رویدادها صفحه‌بندی دارد؛ ابتدا ۵۰۰ رویداد آخر دریافت می‌شود و رویدادهای قدیمی‌تر در دسته‌های ۳۰۰تایی بارگذاری می‌شوند. نمودار امتیاز، منابع و سلامت از رویدادهای ذخیره‌شده ساخته می‌شود.

پشتیبان منطقی مدیر همهٔ ردیف‌های بازی همان مسابقه را صادر می‌کند. Auth، کلیدها و plaintext رمز در آن وجود ندارند. پشتیبان Auth، تنظیم SMTP و سیاست نگهداری نسخه‌های پشتیبان مسئولیت محیط Supabase مقصد است.
